# 自建内容后台与 GitHub 发布方案

确认日期：2026-09-24。用户已确认此架构方向及草稿保密、预览权限、图片访问和错开编辑的约定；尚未实现或通过 PoC。此方案替代外部 CMS 产品选型，六个公开页面的内容范围保持不变。

## 访问与数据流

```text
访客 → React 官网 → 已成功部署的公开内容
                 → 独立 Event Source → Eventbrite

管理层 → /admin → 登录验证 → 内容保存接口 → GitHub 内容文件
                                             ↓
                                         自动构建发布

技术部 → GitHub 修改页面代码 → 自动构建发布
```

- 访客无需账号，公开站点不依赖编辑者登录、GitHub API 或保存接口实时可用。
- `/admin` 不进入六项公开导航，只允许受邀管理层登录；知道链接不代表有编辑权限。
- 内容保存接口可用 Serverless Function 实现，只处理内容编辑与发布，不发展成通用社团后端。
- Eventbrite 读取接口与内容发布独立；构建不要求 Eventbrite 请求成功。普通活动不写入 GitHub 内容文件。
- 不恢复旧 Spring Boot、用户表、会员、JWT 登录流程、RBAC、报名、优惠券等系统。管理登录使用独立身份服务，具体服务在 PoC 中确定。

## 编辑与账号边界

- 管理层在固定中文表单中编辑六页清单允许的文字、图片、链接、列表顺序、公开状态及适用的预设颜色，不接触代码或 GitHub。
- 技术部在 GitHub 维护 React 布局、样式和技术实现。公开站点与后台代码分开组织，不复用旧 AdminView。
- 用户确认技术部同学编辑前先沟通并错开时间，作为避免冲突的主要工作约定；第一版不做复杂协同编辑或自动合并，只保留简单版本检查，防止旧页面保存覆盖新内容。
- 身份、图片存储和部署服务归属学联公共邮箱，由管理层持有账号，技术部获得维护权限。后台编辑者通过邀请获得个人访问，不要求共享管理员密码。
- 第一版不做自动换届、自动撤销离任权限、自助邀请页面或复杂角色；继续协助的离任人员可保留权限。通过身份服务或受保护配置保留人工邀请和撤销方式，撤销后服务端应拒绝后续写入。
- 身份名单和服务凭据不得进入公开内容文件；每次保存、上传、预览和发布均在服务端验证登录身份及编辑权限。

## 内容与图片

- 结构化内容使用 JSON 等非执行文件，与页面代码分离。例如 `content/home.json`、`content/teams/2026.json`、`content/brand-events/<slug>.json`、`content/recruitment.json`、`content/settings.json`。这些是结构示例，不代表已经创建或锁定仓库布局。
- 服务端按固定内容类型映射允许的文件路径，校验字段、长度、链接、年份和引用，不接受浏览器指定任意仓库、分支或文件路径，不允许修改代码、工作流和身份配置。
- GitHub 写入凭据只在服务端使用，优先验证仅安装到所需仓库的 GitHub App。仓库级写权限不能当作目录级隔离，内容路径限制仍必须由服务端执行；不授予不需要的工作流写权限。
- 图片存独立图片服务，内容文件仅存引用和替代文字；上传需验证权限、文件类型、大小并压缩，不恢复旧 MinIO。
- 新上传的未发布图片默认使用受保护访问，确认发布时再开放对应公开版本；不能仅因页面未展示就认为图片 URL 保密。已公开的正式 Logo 等素材不需要重新私有化。保留历史发布需要的图片，避免恢复内容后图片已经丢失。

## 草稿、预览与发布

1. 编辑内容并保存草稿，与线上版本分离。公开 GitHub 仓库的草稿分支不能满足私密草稿要求；PoC 检查现有仓库可见性，内容与代码可分仓：若代码仓库保持公开，则新增独立私有内容仓库；若现有仓库已私有，可评估同仓隔离。具体仓库布局在 PoC 中确定，现有仓库可见性不自动改变。
2. 预览绑定明确内容版本，只允许受邀人员访问；草稿、源文件和草稿图片不能混入公开构建产物，隐藏链接或 `noindex` 不作为权限措施。
3. 发布前再次校验当前内容版本。发生并发修改时拒绝覆盖并提示重新加载；多个文件的相关修改作为一致版本发布。重复请求使用同一发布标识，避免重复提交或构建。
4. 发布只包含已确认的内容变更。不能合并整个陈旧草稿分支而回退代码或夹带其他人的草稿；代码使用已验收的稳定版本，开发中的代码留在开发分支。
5. 自动构建绑定明确的代码版本和内容版本，记录提交与部署标识。后台区分“草稿已保存”“发布中”“已上线”“发布失败”；写入 GitHub 成功不代表部署成功。
6. 成功构建才替换线上版本；失败时上一成功部署继续可用。连续发布应串行或有版本检查，旧构建后完成时不能覆盖新部署。
7. 第一版由技术部使用 Git 历史恢复内容、通过部署平台回滚，不开发完整历史版本管理界面。不强制增加多级审批。

已公开内容撤下后不能保证重新保密，访客可能已保存，Git 历史或公开图片也可能留存；本规则保证首次发布前的草稿不提前公开，不承诺撤回所有已传播副本。

GitHub、身份服务或内容保存接口不可用时，可以暂停编辑／发布，但已有官网继续提供成功部署内容。发布存在构建延迟，不承诺点击后立即生效；实际耗时和费用在 PoC 中记录。

## Eventbrite 保持独立

- 读取或同步失败时，活动列表和详情显示“活动信息暂时无法加载，请稍后重试”，不能显示“暂无活动”。
- 自动重试或定时同步继续运行，成功后自动恢复，无需管理层或技术部手动部署。故障不影响首页、团队、品牌活动等内容页面的展示与发布。
- 不强制保留旧活动快照；API 恢复不应依赖内容 Git 提交或网站重新发布。具体同步周期、恢复延迟及已打开页面的刷新机制在独立 Eventbrite PoC 中验证。

## Step 3 最小验证与通过标准

先用一个受邀测试账号打通“修改首页简介 → 保存草稿 → 预览 → 发布 → 官网更新 → 技术部恢复旧版本”，再验证团队年份、品牌活动、招新和图片，不先完成全部后台。

必须取得实际验证结果：

- 未受邀请求、失效会话和越权文件写入被拒绝；写入凭据不在前端；会话方案包含适当的 CSRF 防护。
- 未登录访客直接请求草稿文件、预览链接和新上传的草稿图片均不能读取；确认发布时只开放所选版本及对应图片，不暴露其他草稿。
- 两人同时编辑、技术部修改代码、重复发布和构建乱序不造成覆盖或混合发布。
- GitHub 提交实际触发构建并可查询最终状态；验证选定凭据、分支保护、工作流与部署平台的兼容性，日常发布不需要技术部人工解锁。
- GitHub 或构建失败时已发布内容可访问，错误发布可恢复，图片仍可用。
- 管理层能独立完成表单编辑发布，Eventbrite 故障不阻断这条流程。

身份服务、仓库是否分离、GitHub App 配置、图片服务、部署平台、成本和发布时延在 PoC 中确定。若验证不通过，先修正发布链路，不将未经验证的方案标记为上线可用。

## 技术依据

2026-09-24 核对官方文档：GitHub 文件更新接口要求已有文件的 SHA，可用于检测并发修改；接口和服务端仍需处理冲突及多文件一致性，见 [Repository contents API](https://docs.github.com/en/rest/repos/contents)。

不能假定任意自动提交都会启动下一次工作流：使用 Actions 自带 `GITHUB_TOKEN` 推送通常不会触发新的 push 工作流。应验证 GitHub App、明确触发事件或部署集成的实际行为，见 [Trigger a workflow](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)。
