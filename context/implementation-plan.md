# 新南学联网站简化改造实施顺序

## 第一阶段 架构审计与归档

1. 盘点前端、后端、路由、API、数据库、共享组件、样式、品牌资产和部署配置。
2. 将现有模块标记为 `KEEP`、`REPLACE`、`REMOVE` 或 `UNKNOWN`，形成依赖清单。
3. 确认旧功能与新版公共页面之间的共享组件、工具、样式和资源依赖。
4. 为当前完整系统创建归档分支或 Git 标签，例如 `archive/full-platform-before-simplification`。
5. 停止为旧系统增加新业务功能。
6. 导出现有数据库中需要保留的活动、部门、团队和历史内容。
7. 整理现有图片，确认哪些是真实社团资产、哪些只是临时占位图。
8. 核对 `frontend/public/brand/` 中的正式品牌资产，补充缺失的 favicon、Logo 版本、字体授权和使用说明。

## 第二阶段 内容和需求冻结

1. 确认一级导航只包含首页、关于我们、部门与团队、品牌活动、全部活动和加入我们。
2. 确认各页面的内容范围、字段和不需要实现的功能。
3. 确认普通活动与品牌活动的边界：普通活动是来自 Eventbrite 的实际发布和报名活动；品牌活动是 CMS 中人工整理的历史代表性内容。
4. 确认普通活动与品牌活动不需要建立数据关联，也不在 CMS 中复制普通活动。
5. 确认 Eventbrite 社团账号、活动数据权限和凭据管理方式。
6. 确认 CMS 编辑者、Eventbrite 活动负责人和技术维护者的职责边界。
7. 确认需要迁移的正式文案、团队资料、品牌活动、荣誉和联系方式。
8. 以后新增字段、筛选项或页面必须有明确用户需求，不为技术完整性扩大范围。

## 第三阶段 数据源 PoC

### CMS PoC

1. 选择一个候选轻量内容管理方案进行小规模验证，不在此阶段完成全部后台。
2. 验证按自然年管理团队并设置当前年份。
3. 验证品牌活动的名称、短介绍、封面、预设主题颜色、重要数据、照片、顺序和公开状态。
4. 验证招新开放和关闭状态、招新时间、开放部门和申请链接。
5. 验证图片上传、尺寸限制、压缩和发布流程。
6. 验证非技术人员能否独立完成一次内容修改和发布。
7. 验证 React 可以通过独立的 Content Source 适配层读取内容。

### Eventbrite PoC

1. 使用少量真实活动验证 Eventbrite API 权限和稳定性。
2. 确认活动标题、简介、图片、时间、地点、状态和报名链接的实际返回字段。
3. 验证 `Australia/Sydney` 时区处理。
4. 验证延期、取消、重复场次、无图片和无地点等情况。
5. 验证服务端读取凭据，不在浏览器中暴露密钥。
6. 验证缓存最后一次成功结果，并在同步失败时继续提供旧数据。
7. 验证 React 可以通过独立的 Event Source 适配层读取活动。
8. PoC 通过后再确定最终 CMS、Event API / Cache 和部署形态。

## 第四阶段 建立新版前端骨架

1. 保留 React、TypeScript、Vite 和 React Router。
2. 先从导航和 Router 中停用登录、个人中心、优惠券、后台、数据面板、美食地图和 AI 助手，并将旧模块与新版页面隔离；此阶段不物理删除旧代码。
3. 建立首页、关于我们、部门与团队、品牌活动、全部活动和加入我们的路由。
4. 提前确定品牌活动和普通活动详情页的稳定 URL 或 slug 规则。
5. 建立统一的页面布局、导航栏和页脚。
6. 建立统一的按钮、标题、卡片、图片比例和响应式规则。
7. 按照 `context/brand-guidelines.md` 建立 CSS 品牌变量，并复用 `frontend/public/brand/` 中的正式资产。
8. 整理全局站点配置和 Instagram、小红书、微信公众号、抖音及 Eventbrite 入口。
9. 从页面骨架阶段使用语义化 HTML，并确定 `h1`、页面标题、描述、canonical URL 和 Open Graph 的基础规则。
10. 完成移动端导航和基础无障碍支持。
11. 将 `.DS_Store` 加入 Git 忽略规则，不将其作为项目资产提交。

## 第五阶段 页面和数据源实现

### 页面实现

1. 按照简化结构重做首页。
2. 重做关于我们页面，并把联系方式放在页面末尾。
3. 重做部门与团队页面，实现按自然年切换和归档。
4. 建立只展示已结束活动的品牌活动列表和详情页。
5. 重做全部活动页面，只提供年份和月份选择，并在卡片上显示活动状态。
6. 重做加入我们页面，只支持招新开放和关闭两种状态。
7. 加入统一页脚和社交媒体入口。
8. 删除重复、过长或没有明确用途的内容。

### CMS 实现

1. 完成首页、关于、部门、团队、品牌活动、加入我们和网站设置的数据结构。
2. 限制编辑者只能修改内容，不允许修改页面结构、字体、CSS、HTML 或任意颜色。
3. 确保 CMS 数据模型不保存普通活动副本，也不负责 Eventbrite 同步或缓存。
4. 通过独立的 Content Source 适配层向 React 提供官网内容。

### Eventbrite 实现

1. 优先采用定时 Serverless Function 或构建时任务完成同步，不建立长期运行的通用后端；具体平台在 PoC 后确定。
2. 建立活动数据缓存并记录最后成功同步时间。
3. 同步失败时保留上一份成功数据，不清空活动列表。
4. 根据时间和 Eventbrite 状态自动计算即将举行、进行中、已结束和已取消。
5. 将报名按钮改为跳转 Eventbrite。
6. 将 Event API / Cache 保持为独立只读模块，不复用 CMS 数据模型，也不发展成通用业务后端。
7. 通过独立的 Event Source 适配层向 React 提供活动，并确保活动模块不依赖 CMS 可用性。

## 第六阶段 内容迁移和视觉完善

1. 迁移学联正式介绍、发展历史和联系方式。
2. 迁移部门信息和历届团队。
3. 选择已经结束的代表性品牌活动并整理内容。
4. 迁移学联荣誉与影响力 bullet point。
5. 使用真实活动照片替换临时网络图片。
6. 压缩并统一活动封面、团队照片和品牌活动图片比例。
7. 完成页面标题、描述、分享图片和其他基础 SEO 内容。
8. 检查所有外部链接和 Eventbrite 报名入口。
9. 检查 Header、页脚、社交入口和品牌背景是否使用正确的 `/brand/...` 资源。
10. 确认品牌背景只作为有限装饰使用，不覆盖长篇正文或重复铺满页面。

## 第七阶段 测试和上线

1. 测试手机、平板和桌面布局。
2. 测试主流浏览器。
3. 测试键盘操作、图片替代文字、语义化标题和颜色对比度。
4. 测试团队年份切换。
5. 测试活动年份和月份选择。
6. 测试所有活动状态和空数据状态。
7. 模拟 Eventbrite 同步失败并确认旧数据仍然显示。
8. 自动检查内部链接以及 Instagram、小红书、抖音、Eventbrite、邮箱和正式文件等外部入口；微信公众号和二维码进行人工验证。
9. 测试超长中文姓名、超长英文职位、超长活动标题和超长地点。
10. 测试缺少图片、简介为空、某年没有团队以及某月没有活动等情况。
11. 测试图片比例错误和品牌活动重要数据数量异常时的显示效果。
12. 让没有代码基础的成员测试更新团队、品牌活动和招新信息。
13. 检查 Logo 在不同屏幕尺寸下不变形、不裁切并保持清晰。
14. 检查品牌颜色和文字背景组合满足对比度要求。
15. 修复测试中发现的问题。
16. 发布新版并观察运行情况。

## 第八阶段 退役旧系统

1. 确认新版稳定且需要保留的数据已经迁移。
2. 物理删除已经停用且确认不再被新版引用的旧前端模块、API 调用、共享代码和样式。
3. 关闭旧版注册、登录、报名、优惠券和管理接口。
4. 停止 Spring Boot、MySQL、Redis、RabbitMQ 和 MinIO 服务。
5. 撤销不再使用的 JWT、SMTP、AI、地图和存储密钥。
6. 按照社团的数据保留要求处理旧用户和报名资料。
7. 删除生产环境中不再需要的容器、端口和服务配置。
8. 保留旧系统归档分支或标签，不在新版主分支继续维护旧业务。

## 第九阶段 文档和交接

1. 编写简短的非技术维护手册。
2. 说明如何发布 Eventbrite 活动。
3. 说明如何更新团队、品牌活动、招新信息和联系方式。
4. 记录域名、部署平台、内容后台、Eventbrite 和同步任务的账号归属。
5. 说明 Eventbrite 同步失败、外部链接失效和网站发布失败时的处理方式。
6. 所有关键账号使用社团公共邮箱，并至少设置两名管理员。
7. 开启双重验证和自动续费提醒。
8. 确保新负责人可以在 30 分钟内学会常规维护。
