# 新南学联网站简化改造实施顺序

最后更新：2026-09-24

## 执行与验收原则

- 已确认采用自建 `/admin` → 登录验证 → 内容保存接口 → GitHub 内容文件 → 自动构建发布，技术部通过 GitHub 修改页面代码；架构与风险边界见 `admin-publishing-architecture.md`，不再进行外部 CMS 产品选型。

- 保留九阶段主线。范围和数据模型先确认，正式文案、照片和品牌资料可持续收集，不要求全部到齐才能进行 PoC。
- 每阶段记录完成证据、未完成项及其阻塞范围，并同步 `project-status.md`；不能把待办或模拟结果标记为真实验证通过。
- Eventbrite 读取或同步失败时，活动列表和详情显示“活动信息暂时无法加载，请稍后重试”，不能显示“暂无活动”。自动重试或定时同步继续运行，后续成功读取后自动恢复展示，无需手动部署。故障只影响活动列表和详情，不影响首页、团队、品牌活动等官网内容页面的展示与发布。
- 不强制保存最后成功活动快照；缓存为可选优化。同步、重试间隔和恢复延迟在 PoC 中明确。

## 第一阶段 架构审计与归档

1. 盘点前端、后端、路由、API、数据库、共享组件、样式、品牌资产和部署配置。
2. 将现有模块标记为 `KEEP`、`REPLACE`、`REMOVE` 或 `UNKNOWN`，形成依赖清单。
3. 确认旧功能与新版公共页面之间的共享组件、工具、样式和资源依赖。
4. 为当前完整系统创建归档分支或 Git 标签，例如 `archive/full-platform-before-simplification`。
5. 停止为旧系统增加新业务功能。
6. 确认需要保留的数据与文件来源；已知且可访问的数据按需导出，未知远程部署记录为退役前必须核实的待办。确认从未部署时，相关导出项可标记为“不适用”。
7. 整理现有图片，确认哪些是真实社团资产、哪些只是临时占位图。
8. 核对 `frontend/public/brand/` 中的正式品牌资产，记录缺失的 favicon、Logo 版本、字体授权和使用说明，取得正式资料后补充，不自行生成替代品。

### 完成条件

- 归档、模块分类和依赖盘点完成；已知数据来源及未确认项有记录。
- 未取得的品牌资料、尚未确认的远程部署不阻止进入第二阶段，但未确认的旧数据和服务不得删除或关闭。

## 第二阶段 内容和需求冻结

2026-09-24 进度：六页范围、编辑边界与管理职责已确认；已有 Eventbrite 官方账号，所有管理层均可进入。身份、图片存储和部署等服务统一使用学联公共邮箱注册，管理层持有账号，技术部获得维护权限。技术部需要 Eventbrite API 访问时联系技术部部长；部长具有账号访问权限，必要时联系其他管理层同学协调授权。实际 API 权限、凭据配置和真实活动读取在第三阶段验证。第二阶段需求冻结完成；后台访问不代表 API 读取已验证。以下条目保留作验收清单。

1. 确认一级导航只包含首页、关于我们、部门与团队、品牌活动、全部活动和加入我们。
2. 确认各页面的内容范围、字段和不需要实现的功能。
3. 确认普通活动与品牌活动的边界：普通活动是来自 Eventbrite 的实际发布和报名活动；品牌活动是内容后台中人工整理的历史代表性内容。
4. 确认普通活动与品牌活动不需要建立数据关联，也不在内容后台中复制普通活动。
5. 确认 Eventbrite 社团账号、活动数据权限和凭据管理方式。
6. 官网内容维护与 Eventbrite 活动管理由每年的管理层负责，技术维护由技术部同学负责；落实具体账号权限及年度交接安排。
7. 正式资料清单在后续页面布局调整后，按实际内容区块建立并补充，由当年管理层核实；第二阶段先确认内容范围，不要求提前建立完整资料清单或收齐资料。
8. 以后新增字段、筛选项或页面必须有明确用户需求，不为技术完整性扩大范围。
9. 确认加载、成功但无数据、读取失败三类状态，以及活动故障隔离和自动恢复要求。
10. 身份、图片存储和部署等服务统一使用学联公共邮箱注册，由管理层持有账号，技术部获得维护权限；具体邮箱、成员邀请和权限配置在产品确定后落实。创建账号时配置至少两名管理员并开启双重验证，涉及付费服务时设置续费提醒。

### 完成条件

- 页面范围、字段和数据边界已冻结；内容、活动及技术维护职责明确。
- Eventbrite 账号和权限申请路径有记录，真实 API 验证前必须取得所需权限。正式资料清单待布局调整后补充，不阻止本阶段完成或 PoC，但不能编造上线资料。

## 第三阶段 数据源 PoC

2026-09-24 进度：本地简介编辑与发布原型已开始，启动及验证说明见 `../frontend/poc/README.md`。本地测试会话和 JSON 发布不能代替以下真实身份、GitHub 自动部署及 Eventbrite 验收。

### 内容后台 PoC

1. 先打通最小流程：受邀登录 → 修改首页简介 → 保存草稿 → 受保护预览 → 发布 GitHub 内容提交 → 自动构建 → 官网更新 → 技术部恢复旧版本。暂不扩展全部后台。
2. 验证按自然年管理团队并设置当前年份。
3. 验证品牌活动的名称、短介绍、封面、预设主题颜色、重要数据、照片、顺序和公开状态。
4. 验证招新开放和关闭状态、招新时间、开放部门和申请链接。
5. 验证图片上传、尺寸限制、压缩和发布流程。
6. 验证非技术人员能否独立完成一次内容修改和发布。
7. 验证 React 可以通过独立的 Content Source 适配层读取内容。
8. 验证草稿私有保存、预览需要登录、新上传未发布图片默认受保护；直接访问文件或图片也不能绕过权限。发布仅开放确认版本及对应图片，记录内容生效时间。
9. 验证 GitHub、身份或保存接口故障以及构建失败时，已有公开页面仍可访问；后台区分草稿已保存、发布中、已上线及失败。
10. 验证未受邀请求、越权路径及非法字段被服务端拒绝，GitHub 写入凭据不进入浏览器，草稿和预览未公开。
11. 技术部按编辑前沟通、错开时间的约定操作，不开发复杂协同编辑；验证简单版本检查能防止旧页面保存静默覆盖新内容；重复发布不会生成重复任务，较旧构建不能覆盖较新部署。
12. 验证技术部代码发布与管理层内容发布互不夹带未完成改动；PoC 检查仓库可见性：公开代码仓库搭配独立私有内容仓库，现有私有仓库可评估同仓隔离；验证草稿隔离和稳定代码版本选择，不自动改变现有仓库可见性。
13. 用选定 GitHub 凭据与部署平台实际验证自动触发，不以提交成功作为上线成功；记录费用、构建额度与预计发布延迟。

### Eventbrite PoC

1. 使用少量真实活动验证 Eventbrite API 权限和稳定性。
2. 确认活动标题、简介、图片、时间、地点、状态和报名链接的实际返回字段。
3. 验证 `Australia/Sydney` 时区处理。
4. 验证延期、取消、重复场次、无图片和无地点等情况。
5. 验证服务端读取凭据，不在浏览器中暴露密钥。
6. 验证首次读取失败、同步失败和分页部分失败均显示“活动信息暂时无法加载，请稍后重试”；成功返回零活动时才显示空数据状态。
7. 验证 React 可以通过独立的 Event Source 适配层读取活动。
8. 验证故障后自动重试或定时同步仍运行，服务恢复后无需手动部署即可重新展示；明确间隔、允许的恢复延迟和已打开页面的恢复机制。
9. 验证活动故障不会阻止官网内容页面的展示或发布，内容后台不可用也不阻断独立的活动读取。
10. 不将旧数据展示或持久快照设为通过条件；缓存是否需要由实际访问需求决定。

### 部署验证与完成条件

- 在候选部署平台跑通内容后台发布及活动自动读取／同步，确认凭据隔离、费用、平台限制和账号归属。
- 明确详情页 SEO 与分享信息所需的静态生成或预渲染方案，以及内容更新方式；不将 Eventbrite 成功响应设为全站构建的必要条件。
- 为各 PoC 约定验证范围和时间上限，记录通过或不通过结论、证据与阻塞项。候选方案不通过时记录原因再更换，不直接进入全面实现。
- 凭据未到位时可继续内容整理和接口设计，不能以模拟数据替代真实 API 验收。
- 两个 PoC 和部署验证通过后确定身份服务、GitHub 写入和草稿策略、图片存储、独立活动适配层及部署形态。

## 第四阶段 建立新版前端骨架

1. 保留 React、TypeScript、Vite 和 React Router。
2. 在新版开发与预览环境中先从导航和 Router 中停用旧公众登录、个人中心、优惠券、旧后台、数据面板、美食地图和 AI 助手，并将旧模块与新版页面隔离；此阶段不物理删除旧代码，不提前切换现有生产站点。
3. 建立六个公开页面路由，以及隔离旧 AdminView 的新 `/admin` 登录和内容编辑入口；后台不计入一级导航，公开页面不依赖后台会话。
4. 提前确定品牌活动和普通活动详情页的稳定 URL 或 slug 规则。
5. 建立统一的页面布局、导航栏和页脚。
6. 建立统一的按钮、标题、卡片、图片比例和响应式规则。
7. 按照 `context/brand-guidelines.md` 建立 CSS 品牌变量，并复用 `frontend/public/brand/` 中的正式资产。
8. 整理全局站点配置和 Instagram、小红书、微信公众号、抖音及 Eventbrite 入口。
9. 从页面骨架阶段使用语义化 HTML，并确定 `h1`、页面标题、描述、canonical URL 和 Open Graph 的基础规则。
10. 完成移动端导航和基础无障碍支持。
11. 检查 `.DS_Store` 忽略规则，并清理新版分支中已跟踪的 IDE 和构建缓存文件；归档保持不变。
12. 建立自动构建与独立预览环境，并实现统一加载、空数据和错误状态。
13. 落实 PoC 确定的 SEO 方案、404 和旧路径重定向；按数据源域名核对浏览器请求策略。

### 完成条件

六个一级入口及详情页骨架可在预览环境访问；构建通过，移动导航可用，公开布局解除旧认证和 AI 依赖。

## 第五阶段 页面和数据源实现

### 实施顺序

先确定两个适配层的数据结构和错误状态，在第三阶段首页简介 PoC 基础上扩展团队年份切换的后台编辑、发布、展示流程，再打通普通活动列表、详情及 Eventbrite 跳转，最后扩展其余页面。下面按模块列出范围，不表示先写完全部页面再接数据。实现过程中验证年份月份过滤、时区与状态边界和故障恢复。

### 页面实现

1. 按照简化结构重做首页。
2. 重做关于我们页面，并把联系方式放在页面末尾。
3. 重做部门与团队页面，实现按自然年切换和归档。
4. 建立只展示已结束活动的品牌活动列表和详情页。
5. 重做全部活动页面，只提供年份和月份选择，并在卡片上显示活动状态。
6. 重做加入我们页面，只支持招新开放和关闭两种状态。
7. 加入统一页脚和社交媒体入口。
8. 删除重复、过长或没有明确用途的内容。

### 内容后台实现

1. 完成首页、关于、部门、团队、品牌活动、加入我们和网站设置的数据结构。
2. 限制编辑者只能修改内容，不允许修改页面结构、字体、CSS、HTML 或任意颜色。
3. 确保内容后台数据模型不保存普通活动副本，也不负责 Eventbrite 同步或缓存。
4. 通过独立的 Content Source 适配层读取成功部署的 GitHub 内容产物，访客访问不实时依赖 GitHub。
5. 实现受邀登录、允许字段和文件路径校验、版本冲突检测、图片上传、草稿预览及发布状态；不复用旧 JWT、用户表或 RBAC。
6. 内容和代码变更均经过自动校验构建，部署绑定明确版本；由技术部通过 Git 历史和部署平台恢复，不先开发复杂历史管理界面。
7. 不开发自动换届撤权、自助邀请页面或多级审批；邀请和人工撤销通过身份服务或受保护配置完成。

### Eventbrite 实现

1. 使用 PoC 验证的服务端只读适配层，采用自动重试或定时同步，不建立长期运行的通用业务后端。若使用构建任务，必须可自动触发恢复且不阻断官网内容页面发布，不能仅靠人工部署拉取活动。
2. 区分成功、空数据和失败，记录读取或同步结果供故障排查；缓存为可选优化，不强制保存旧快照。
3. Eventbrite 读取或同步失败时，活动列表和详情显示“活动信息暂时无法加载，请稍后重试”，不能显示“暂无活动”。自动重试或定时同步继续运行，后续成功读取后自动恢复展示，无需手动部署。故障只影响活动列表和详情，不影响首页、团队、品牌活动等官网内容页面的展示与发布。
4. 使用 `Australia/Sydney` 时区，根据当前时间和 Eventbrite 状态自动计算即将举行、进行中、已结束和已取消；明确取消优先级并验证夏令时边界，时间状态更新不应仅依赖下一次同步。
5. 将报名按钮改为跳转 Eventbrite。
6. 将 Event API / Cache 保持为独立只读模块，不复用内容后台数据模型，也不发展成通用业务后端。
7. 通过独立的 Event Source 适配层向 React 提供活动，并确保活动模块不依赖内容后台可用性。

### 完成条件

所有页面接入对应真实数据源，非技术编辑发布流程可用；活动故障显示、自动恢复及两类数据源的故障隔离已验证。

2. 测试主流浏览器。
3. 测试键盘操作、图片替代文字、语义化标题和颜色对比度。

16. 发布新版并按预先约定的观察期和验收条件观察运行情况。

### 上线与观察条件

- 自动构建、正式域名、服务端凭据、关键链接和数据源读取已验证，非技术成员完成一次实际发布。
- 留存上一版可用部署，记录回滚操作并在预览环境验证；上线前已有基本维护和故障处理说明。
- 上线前约定观察期、维护负责人和阻断问题标准；观察期内完成多次自动读取或同步及一次内容后台更新，确认无阻断问题后再进入退役。
- 如果存在旧生产系统，在切换前明确停止旧报名等写入的时点及最终数据导出安排，避免迁移后继续产生遗漏数据。

## 第八阶段 退役旧系统

1. 确认观察期验收通过、需要保留的数据和文件已迁移、备份可恢复，并取得明确退役确认；尚未核实的远程部署必须先核实。
2. 物理删除已经停用且确认不再被新版引用的旧前端模块、API 调用、共享代码和样式。
3. 关闭旧版注册、登录、报名、优惠券和管理接口。
4. 停止 Spring Boot、MySQL、Redis、RabbitMQ 和 MinIO 服务。
5. 确认不再需要旧服务回滚后撤销旧密钥，避免提前破坏恢复能力。
6. 按社团的数据保留要求处理旧用户和报名资料；永久删除数据或备份须单独明确确认。Git 归档不能代替数据库及上传文件备份。
7. 删除生产环境中不再需要的容器、端口和服务配置。
8. 保留旧系统归档分支或标签，不在新版主分支继续维护旧业务。

### 完成条件

确认停用范围、数据去向和恢复资料已记录，旧代码及基础设施按授权退役。确认从未部署的服务，其生产停机和导出操作标记为“不适用”，不编造执行记录。

## 第九阶段 文档和交接

1. 整理从 PoC 起持续记录、上线前已具备的非技术维护手册。
2. 说明如何发布 Eventbrite 活动。
3. 说明如何更新团队、品牌活动、招新信息和联系方式。
4. 记录域名、部署平台、内容后台、Eventbrite 和同步任务的账号归属；年度换届时由管理层交接内容后台与 Eventbrite 管理权限，技术部交接技术维护资料与访问权限。
5. 说明 Eventbrite 同步失败、外部链接失效和网站发布失败时的处理方式。
6. 核对第二阶段起落实的账号归属，确认关键账号使用社团公共邮箱并至少设置两名管理员。
7. 核对双重验证、账号恢复方式及适用服务的续费提醒；不强制自动撤销离任人员权限，记录继续协助者，保留人工撤销方式。
8. 让新负责人依据手册在 30 分钟内完成常规维护操作，记录交接结果和仍需协助的事项。
